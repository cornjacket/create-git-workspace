# 22 — one repo's missing task folder silently truncates the whole replan

Status: **filed 2026-08-04**, found while drafting plans for the full roster.

`make replan` exits 1 with **no error message** partway through the roster.
Every repo after the offending one never gets a plan, and nothing says so.

## Reproduction

```
$ make replan
==> Redrafting daily plans for 2026-08-04
    _workspace               already current
    captains-log             already current
    create-project-system    no task-system — skipped
    create-git-workspace     no task-system — skipped
make: *** [replan] Error 1
```

Three registered repos — `create-ai-builder`, `second-brain-devkit`,
`customer-req-responder` — are simply absent from that list. Not skipped, not
failed: **unmentioned**. The run died on the fourth.

## Cause

`replan.sh:110` collects the Triage section from two folders:

```bash
{ list_folder "$tasks" inbox; list_folder "$tasks" draft; } | bullets "_Nothing in triage._"
```

with `set -euo pipefail` in force. `create-ai-builder`'s task-system was
generated by an **older `create-project-system`** whose epic has no `inbox`
folder:

| repo | folders under the epic |
|---|---|
| `captains-log` | backlog complete draft in-progress **inbox** wont-do |
| `create-ai-builder` | backlog complete draft in-progress wont-do |

`list-tasks.sh --folder inbox` exits 1 there. `pipefail` propagates it, `set -e`
takes the whole script down, and because the progress line is printed *after* a
repo is drafted, the repo that killed the run is never even named.

## This is the open question landing, harder than predicted

`PLAN.md` already carries: *"per-repo replan couples to the child's task-system
internals — it probes the layout, calls `list-tasks.sh`, scrapes its human
output with `sed`, and assumes the folder vocabulary."* The predicted failure
was a **silent wrong answer** (`_Nothing in progress._` where there is work).

The real failure is worse in the dimension that matters: not one wrong plan, but
**every subsequent repo silently losing its plan**. It is task `16`'s shape
again — the system omits work and reports success-shaped output — and it is the
second time in one day that a `continue`/exit path has dropped repos without a
trace.

The recorded lean was *"(e) verify the interface before trusting it, and skip
loudly when it does not match."* That is exactly right and now has a trigger.

## The fix

1. **A missing folder is not an error.** Absent `inbox` means "no inbox", not
   "failure" — tolerate a non-zero `list_folder` for a folder that does not
   exist, the way an empty one is already tolerated.
2. **One repo must never truncate the roster.** Draft each repo in a subshell
   whose failure is caught, then report per-repo status and a non-zero exit at
   the *end*. A batch verb that stops at the first bad row is unusable across a
   growing roster.
3. **Name the repo you are working on before you work on it.** The progress line
   prints after drafting, so a crash hides its own cause. Print on entry.
4. **Verify the interface up front** (option (e)): probe the folder vocabulary
   once per repo and skip *loudly* on a mismatch, rather than discovering it
   through an exit code mid-pipeline.

## Wider consequence worth deciding

`create-ai-builder`'s task-system is a version behind, and this is the first
time that mattered. Either the workspace tolerates a range of vocabularies, or
child task-systems need a declared version — the `(b)` option already listed
under the open question. Tolerance is the cheaper first move; a declared version
is the honest one if the vocabulary keeps drifting.

## Acceptance

- `make replan` drafts **every** enabled repo, whatever folders each epic has.
- A repo that cannot be drafted is named, with a reason, and the run continues.
- The exit code still reflects that something was skipped — loudly, at the end.
- A test covers a child whose epic lacks `inbox`; today's suite passes while the
  real roster cannot be drafted, which is why this reached production.
